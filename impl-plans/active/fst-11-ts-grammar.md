## Intent and Context

The user wants a syntax for `.vact` that runs as WASM on the web, and
asked whether tree-sitter (C) can be ported to WASM. The answer is in
design section 2: yes, `tree-sitter build --wasm` compiles the generated
C parser and a C scanner to WASM with no emscripten. This plan creates
the top-level `tree-sitter-vact/` grammar, which exists for the editor
only. Its job is highlighting and folding. The Rust reader stays the
source of truth for the language. The grammar must parse every committed
`.vact` file with zero `ERROR` and zero `MISSING` nodes. It may accept
more than the reader does.

This plan also owns every `mise.toml` and `.gitignore` edit of the whole
change, so no other plan touches those files. FST-23 consumes the node
types and capture names pinned below.

## Non-goals

- No `package.json`, `bindings/`, `Cargo.toml`, `binding.gyp`,
  `locals.scm` or `indents.scm`. Do not run `tree-sitter init`, because
  it generates bindings.
- No Rust dependency on tree-sitter. Do not touch `Cargo.toml` or `src/`.
- No tree structure below the statement level (pipes, operators and
  precedence stay flat, per 4.1).
- No emscripten or docker; no `--docker` flag.
- Do not commit `tree-sitter-vact.wasm` or any other build output.

## Contract (pinned; FST-23 depends on it)

- **Node types** (design 4.4): `source_file`, `statement`,
  `continuation`, `block`, `group`, `list`, `pair` (fields `key` and
  `value`), `string`, `string_content`, `escape_sequence`,
  `interpolation`, `comment`, `directive`, `identifier`,
  `qualified_identifier`, `keyword`, `number`, `path`, `url`,
  `operator`, `wildcard`, `console_register`, `block_colon`. The
  brackets `{ } [ ]` are anonymous nodes, and the same anonymous `{`/`}`
  is used inside `interpolation`.
- **Captures** (4.5): `@comment`, `@comment.directive`, `@string`,
  `@number`, `@string.special.symbol`, `@string.special.path`,
  `@keyword`, `@punctuation.bracket`, and no others. The `@keyword`
  pattern matches the FIRST `identifier` child of a `statement` or a
  `group`, with
  `(#any-of? @keyword "let" "var" "upd" "fn" "inst" "bus" "look" "master" "import" "slot" "if")`,
  listed in exactly that order (it equals `HEADS`).
- `folds.scm` is exactly `(block) @fold`.
- `tree-sitter.json`: one grammar with `name` "vact", `camelcase`
  "Vact", `scope` "source.vact", `path` ".", `file-types` ["vact"], and
  `highlights` "queries/highlights.scm". `metadata` has `version`
  "0.1.0", `license` "MIT" (the crate's license), a description and
  `links.repository`. Set every binding to `false`.
- Build output: `tree-sitter-vact/tree-sitter-vact.wasm`, which is
  ignored.

## Implementation Key Points

1. **Externals order.** Declare, in this order: `_newline`, `_indent`,
   `_dedent`, `_continuation`, `block_colon`, `string_content`, and an
   error sentinel. The scanner's enum must match the order exactly.
2. **Indentation.** Only CODE lines count. Blank lines and comment-only
   lines never emit `_indent` or `_dedent`, whatever their
   indentation; this mirrors `layout.rs`. The comments themselves are
   `extras`, lexed by the internal lexer. Follow how the python scanner
   handles comment lines: it must not decide the indent from a comment
   line.
3. **Width.** Count tabs, and count a space as width 1 (lenient).
4. **Continuation.** Emit `_continuation` at a line break when the next
   code line is deeper than the current statement line and starts with
   `>` but not `>=`. A deeper line right after a line ending in a block
   colon is `_indent`, never a continuation (design 6.5.4: there, `>` is
   greater-than). Blocks opened on a continuation line push the level of
   that continuation line + 1.
5. **block_colon.** Emit it only for a `:` followed by nothing but
   spaces or tabs, then `#`, a line end or EOF, using lookahead with
   `mark_end`. Leave every other `:` to the internal lexer: a pair
   colon (`key:` then a space) or `:name`. Pitfalls: in `:drums:` and
   `0.8:` the trailing `:` is a block colon, and `->:` is `->` then a
   block colon.
6. **Strings.** Strings are on one line. `string_content` is external
   and covers any run of bytes except `"`, `\`, `{` and newline,
   including leading spaces and `#`. This keeps `#` inside a string from
   becoming a comment extra. A bare `}` inside a string is content.
   Interpolation is `{` items `}` and nests (strings inside it).
7. **Identifiers.** `sample-play` is one identifier. `a->b` is three
   tokens: an inner `-` segment must be followed by a word byte, which
   the regex expresses without lookahead. Copy the character classes
   from `lexer.rs`, and do not invent new ones.
8. **Scanner hygiene.**
   - Indent stack capped at 128 entries.
   - `serialize` and `deserialize` store the full state within 1024
     bytes, and `deserialize(NULL, 0)` resets it.
   - `scan` returns false when every symbol is valid (error recovery).
   - Use only `calloc`, `free`, `memcpy` and `memset`, which are in
     tree-sitter's wasm stdlib.
   - No global mutable state; allocate in `create`.
9. **Leniency.** A statement is flat: its first line's items, then any
   `continuation`s, then an optional `block_colon` and `block`. Items are
   any of the tokens, `group`, `list`, `pair` or `string`. Any operator
   mix, including `- x`, `-1`, `> + {..} > * 0.5` inside groups, must
   parse without ERROR.
10. **Generated files.** Run `tree-sitter generate` with CLI 0.27.0 only,
    and commit its output unmodified. Do not pass `--abi`.
11. **Cache paths.** The Codex sandbox may block `~/.cache/tree-sitter`
    (wasi-sdk) or the compiled-parser cache. If a command fails for that
    reason, record the exact command, its exit code and its stderr in the
    Progress Log as BLOCKED. FST-40 then reruns it outside the sandbox.
    Do not work around it by vendoring toolchains.

- `[tasks.ts-generate]`, with `dir = "{{config_root}}/tree-sitter-vact"`
  and a bash `run` that uses `set -eu`:
  1. Compute `shasum -a 256` of `src/parser.c`, `src/grammar.json`,
     `src/node-types.json` and `src/tree_sitter/*.h`.
  2. Run `tree-sitter generate`.
  3. Compute the hashes again, then fail with a clear message when the
     two lists differ.
- `[tasks.ts-test]`, in the same `dir`:
  1. `tree-sitter test`.
  2. `tree-sitter query queries/highlights.scm test/highlight-sample.txt`
     (the sample file is described below). Fail if the command exits
     nonzero or prints `error`.
  3. `scripts/parse-all.sh`.
- `[tasks.ts-build-wasm]`, in the same `dir`: run
  `tree-sitter build --wasm -o tree-sitter-vact.wasm`, then check that
  the first 4 bytes are `00 61 73 6d` (use `od`, `head -c`).
- `[tasks.fmt-vact-check]`: `git ls-files -z '*.vact' | xargs -0 cargo run --quiet -- fmt --check`
  with `env = { CARGO_TERM_QUIET = "true" }`. This task is defined here
  but can only pass after FST-20 lands. FST-20 verifies it.
- Do not change any other task or tool.
- The query sample `tree-sitter-vact/test/highlight-sample.txt` is

## parse-all.sh

- Run it from `tree-sitter-vact/`. It takes the file list from
  `git -C .. ls-files '*.vact'`, where `ls-files` only reads `.git`. If
  git fails, fall back to `../examples/*.vact` and `../src/prelude/*.vact`.
- For each file, run `tree-sitter parse` and capture stdout. Add
  `--grammar-path .` only if the 0.27.0 CLI supports it; check
  `tree-sitter parse --help`.
- Fail (exit 1, and name the file) when the exit code is nonzero or the
  output contains `ERROR` or `MISSING`.
- Print `parse-all: <n> files ok` on success. `n` must be at least 10.

## Corpus (tree-sitter test)

The corpus must cover these, each with its expected tree:

- a statement with pairs;
- a statement with a deep `>` continuation;
- a block opened by a continuation;
- `inst` with a nested block;
- the `if`/`elif`/`else` chain;
- `->:` lambda;
- `slot :drums gain: 0.8:`;
- `:kw:` followed by a block;
- nested interpolation, escapes, a `#` and a `}` inside a string;
- path (`./a`, `../b`, `~/c`, `/d`) and url literals;
- numbers (int, float, ratio `1/4`, negative);
- `_` and `_1`;
- a qualified identifier;
- own-line comments and directives at odd indentations (no
  indent/dedent effect);
- blank lines inside a block;
- CRLF line ends;
- an EOF without a final newline;
- `a->b`;
- `>=` at a line start after a deeper statement (not a continuation).
